# 继续旧任务和新建任务，有什么不同？

项目相同，不代表每个任务都拥有相同的对话历史。本章只向一个任务交代临时代号，再到新任务和旧任务里问同一个问题，观察答案与请求如何对应。

## 先把信息放在一个任务里

修复完成后，在原 Desktop 任务中发送：

```text
本次会话临时代号是 PRICE-A7。只在本会话中使用，不写入文件，也不要保存为长期记忆。回复收到即可。
```

实际回复“收到。”，没有工具调用。我们特意使用与业务实现无关的代号，避免模型从源码或常识推算答案。

然后在同一个 TS 项目下新建任务，发送：

```text
不读文件、不搜索其他任务。如果当前上下文里有本项目的实验临时代号，请给出；如果没有，请回答不知道，不要猜。
```

新任务回答“不知道。”。再回到原来的任务，发送完全相同的问题，得到 `PRICE-A7`。三次操作均由 Desktop 输入框完成，没有通过委派工具把旧任务正文转交给新任务。

## 对照两个任务的请求

| 操作 | 正式请求 `input` 项数 | `previous_response_id` | 实际回答 |
| --- | ---: | --- | --- |
| 在原任务设置代号 | 1 | 引用先前响应 | 收到。 |
| 在新任务追问 | 7 | 未携带该字段 | 不知道。 |
| 回原任务再次追问 | 1 | 引用设置代号时的响应 | PRICE-A7 |

分别查看[设置代号](../evidence/desktop-lab/08-session-seed/00-request.request.json)、[新任务提问](../evidence/desktop-lab/08-session-new/00-request.request.json)和[原任务追问](../evidence/desktop-lab/08-session-resume/00-request.request.json)。两个任务的 `client_metadata.thread_id` 不同，原任务的设置与追问则共享同一个 ID。

设置代号请求中的这条消息如下。这里省略消息 `id`，保留内容结构：

```json
{
  "type": "message",
  "role": "user",
  "content": [
    {
      "type": "input_text",
      "text": "本次会话临时代号是 PRICE-A7。只在本会话中使用，不写入文件，也不要保存为长期记忆。回复收到即可。\n"
    }
  ]
}
```

新任务的 `input` 中找不到 `PRICE-A7`。原任务追问的当前 `input` 也没有重写代号，但它引用了设置代号那次响应。沿引用可以找到先前信息，因此不能只搜索当前这一份输入就断言遗忘。

## 同一项目，不等于共享聊天历史

新任务仍然可以获得项目环境、规则和可用工具，这些信息来自项目和应用上下文。它们与另一个任务里的临时对话是不同来源。

本次观察到的是：没有读取文件、没有搜索其他任务时，新任务没有给出代号；回到原任务后，可以沿原会话继续使用它。这支持任务历史边界的判断，不证明产品永远不会通过任何功能把信息带到其他任务。

如果把代号写入 `AGENTS.md`，或者显式让新任务读取一个记录文件，那已经改变了信息进入路径，不能再把答对简单归因于“自动记住旧聊天”。

## “回到旧任务”验证到哪一步？

本实验是在 Desktop 中切换任务后继续提问，没有退出应用，也没有模拟进程崩溃。因此它证明的是已有任务的对话接续，不足以证明任意重启或异常恢复都保持相同行为。中断与恢复会在后面的独立实验中观察。

三步分别产生 1 次正式模型请求，均无工具调用，输入 token 分别为 40,174、32,947、40,219，输出分别为 6、44、7。这些统计排除预热，按各自响应记录，不是费用；不同输入量也不能单独当作有没有长期记忆的判据。

## 换个来源，结论会改变吗？

假设新任务通过读取 README 找到了 `PRICE-A7`，你会把它记录为“旧聊天自动延续”还是“文件提供信息”？需要保留哪一份证据？

<details>
<summary>参考解释</summary>

应记录为文件提供信息。需要保留读取调用、包含代号的工具结果和后续回答，才能解释信息来源。新任务最终答对不够证明旧聊天自动延续；本章之所以禁止读文件和搜索其他任务，就是为了减少这些来源的干扰。

</details>
