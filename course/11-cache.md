# 输入很少，为什么仍然有很多 token？

新问题只有几个字，完成事件却报告三万多个输入 token。这个数字可能包含重发或引用的历史，其中又可能有一部分命中缓存。本章用实际用量字段，把新增文字、有效上下文和缓存计数分开。

## 比较已经发生的三次请求

第一章输入“你好”，第二章输入“我刚才说了什么？”，第七章最后一次请求则回传验证结果。下面比较的是各自一份正式完成事件，不是整个实验的合计：

| 样本 | 输入 token | 其中 `cached_tokens` | 输出 token |
| --- | ---: | ---: | ---: |
| 第 1 章正式问候 | 32,774 | 0 | 13 |
| 第 2 章接续对话 | 32,930 | 13,568 | 12 |
| 第 7 章最后阶段 | 39,982 | 38,912 | 151 |

可在[问候完成事件](../evidence/desktop-lab/01-hello/01-request.response.json)、[接续完成事件](../evidence/desktop-lab/02-context/00-request.response.json)和[修复最后阶段](../evidence/desktop-lab/07-fix/04-request.response.json)核对。这些请求在同一次教程实验中也没有固定的缓存命中数量。

## 先找到真正的用量字段

第二章完成事件中的 `response.usage` 包含以下字段。下面是原嵌套结构的节选，省略了其他统计：

```json
{
  "input_tokens": 32930,
  "input_tokens_details": {
    "cache_write_tokens": 0,
    "cached_tokens": 13568
  },
  "output_tokens": 12,
  "total_tokens": 32942
}
```

`cached_tokens` 属于输入详情，不是在 `input_tokens` 之外再增加的一批输入。所以本例不能把 32,930 和 13,568 相加后称为总输入。记录的总 token 是输入加输出：32,930 + 12 = 32,942。

同样，缓存计数为零不代表没有上下文；第一章就携带了应用规则、工具信息和环境，只是完成事件报告的缓存数为零。

## 历史重发、响应引用与缓存不是一回事

第 2 章请求把“你好”和上一轮回答重新放进 `input`，仍报告了 13,568 个缓存输入 token。这说明“线上重发历史”与“模型侧报告缓存命中”可以同时出现。

第 7 章最后请求通过 `previous_response_id` 引用历史，当前 `input` 只有一项工具结果，却报告了 39,982 个输入 token。引用减少了这份请求需要重复写出的内容，但不能仅按当前 JSON 的文字长度理解有效上下文。

本章观察的是服务返回的计数。它没有直接展示内部缓存存储结构、逐块匹配算法，也没有通过控制实验测出缓存给这次响应节省了多少时间。

## 一次任务的合计怎样读？

第 7 章共有五次正式请求。逐次累加，输入为 191,862，缓存输入为 186,240，输出为 1,056。缓存输入合计仍是输入合计的一部分。

这不是五份互不重叠的项目知识。每次模型继续工作，都可能再次处理相同上下文，因此跨请求求和会重复计入历史。想理解任务为什么多次请求，应看工具闭环；想观察每次缓存情况，应看每份响应的用量字段。

这里全部排除预热。第一章另有预热记录，不能悄悄加入问候请求的数字，再与其他章节的正式请求比较。

## 为什么这里不直接算费用？

日志给出了用量事实，但费用还取决于实际模型、服务层与适用计费规则。没有核对这些条件，就不把 token 数乘一个猜测价格，也不承诺命中缓存一定带来某个固定折扣。

本次所有举例中的 `cache_write_tokens` 为 0，只能描述所选事件。它不足以推出“这个系统从不写缓存”，也不能单独说明后续请求一定会命中。

## 练习：只用字段判断

打开第 7 章最后完成事件，计算输入中未计入 `cached_tokens` 的差值。再解释为什么这个差值既不是本轮用户输入长度，也不是费用。

<details>
<summary>参考解释</summary>

39,982 − 38,912 = 1,070。它是该响应两项用量计数的差，仍可能包含新增工具结果和其他上下文，不等于输入框文字长度。费用需要额外的适用计费信息。本章没有用差值推导内部缓存实现。

</details>
