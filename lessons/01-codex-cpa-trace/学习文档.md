## 2. 谁负责什么，流程怎样运行

**Desktop是应用界面，本机由它启动的 Codex App Server 承载 Agent 运行流程。** Harness 是组织上下文、调用模型和执行工具等机制的统称；App Server 是这里对应的具体后台入口。CPA转发请求，上游服务接续历史，模型生成回答或工具调用，本地工具执行实际命令。

## 4. 工具定义、工具调用、工具结果是三件事

| 对象 | 在哪里看 | 含义 |
|---|---|---|
| 工具定义 | 请求的 `additional_tools`，响应顶层的 `tools` | 工具名称、用途、参数格式；相当于菜单 |
| 工具调用 | 响应 `output` 内的 `custom_tool_call` | 模型这一次要求执行的动作 |
| 工具结果 | 下一请求 `input` 内的 `custom_tool_call_output` | 实际执行返回的信息 |

响应顶层 `tools` 是服务返回的工具配置信息，不是这一轮执行过的工具清单。判断是否实际调用，应检查 `output`；判断是否执行成功，应继续看对应的工具结果。

这次模型调用的是 `functions` 命名空间下的 `exec`。该工具接收 JavaScript，JavaScript 再调用 `tools.exec_command`，最终启动本地命令：

```text
模型生成 custom_tool_call
    name = exec
    input = JavaScript代码
        ↓
工具运行环境执行 JavaScript
    await tools.exec_command({cmd: "Get-Content ..."})
        ↓
终端运行 PowerShell 命令
        ↓
执行结果经 text(...) 返回，成为 custom_tool_call_output
```

这几个执行层级不代表额外进行了多次模型推理。一次 exec 可以编排下层工具；这次每次 exec 内都调用了一次终端工具。

## 7. 上下文管理：同轮与跨轮都使用引用接续

这次最值得观察的链条是：

```text
阶段1：初始上下文 → 响应R1（要求读openai-docs）
阶段2：previous_response_id=R1 + 文件读取结果 → R2（第一轮最终回答）
阶段3：previous_response_id=R2 + 第二条用户消息 → R3（要求读focus-coach）
阶段4：previous_response_id=R3 + 技能正文 → R4（要求搜索学习材料）
阶段5：previous_response_id=R4 + 搜索结果 → R5（第二轮最终回答）
```

R1至R5是本文便于阅读的代号。真实ID记录在每份JSON与 [证据索引](evidence/source-index.json) 中；已验证四个引用连续匹配。

阶段3很关键：第一轮虽然已经在聊天窗口结束，第二轮仍引用其最终响应。因此“用户发了新消息”不意味着创建空白上下文。

后续请求没有重新发送AGENTS.md全文，只新增消息或工具结果。CPA的上游请求也保持同样的 `previous_response_id` 与增量 `input`。本次历史接续由上游服务提供；Harness负责维护本地会话、选择新增内容和关联ID。不能因为上游接续，就说Harness不管理上下文。

这里不能观察到上游内部如何存储/拼装历史，也不能据此推断断线恢复、跨协议切换或所有版本都采用同一种方式。

### 三种容易混淆的机制

| 机制 | 本次是否看到 | 能说明什么 |
|---|---|---|
| 引用接续 | 是，previous_response_id | 减少传输的历史正文；不代表历史被遗忘 |
| 提示缓存 | 是，usage报告cached_tokens | 服务报告复用部分输入计算；不等于上下文被删除 |
| 上下文压缩/compaction | 未见相应事件 | 本次无法讲解压缩后的具体结构与恢复行为 |

本次存在工具输出预算配置，但实际结果无截断标记。模型可见的是工具返回内容，不是自动访问整个文件系统。reasoning摘要或加密字段也不等于可读的完整内部思考。

## 8. CPA实际做了什么，日志怎么看

本机链路为 Codex Desktop → `http://127.0.0.1:8317/v1` → CPA → 上游。此次使用WebSocket传输，记录中可见上游连接为 `wss://chatgpt.com/backend-api/codex/responses`；这是实测地址，不是建议自行依赖的公开API契约。

每个阶段保存了三份核心JSON：

- `*-request.json`：Codex发给CPA的消息正文。
- `*-upstream.json`：CPA发给上游的消息正文。
- `*-response.json`：从客户端侧 `response.completed` 中抽出的完整响应对象。

逐字段比较六组请求，值差异均只有上游新增的空字符串 `instructions`；`input` 和 `previous_response_id` 相同。比较忽略顶层对象属性顺序，不对其他提供商作推断。原始请求头未包含在导出文件中。

`*-events.json` 保留该阶段客户端侧的JSON事件序列，用来观察流式响应。常见阅读入口：

| 字段/事件 | 阅读目的 |
|---|---|
| response.create | 一次模型请求正文 |
| response.created | 服务创建响应对象 |
| response.output_item.added / done | 一项输出开始/结束 |
| response.output_text.delta | 流式文字片段 |
| response.completed | 本次响应完成，含output和usage |
| call_id | 工具调用与执行结果配对 |
| previous_response_id | 本次请求引用哪个历史响应 |

两侧各记录一次传输，不是调用次数翻倍；多个delta是同一次响应的片段，也不是每段调用一次模型。预热响应输出为空，但usage仍报告输入计数，不能简单称作“没有任何消耗”。

## 10. 把这次观察转成工程能力

Harness engineering的工作不止写提示词，还包括决定初始上下文放什么、工具接口如何表达、执行结果怎样返回、状态怎样接续、错误怎样反馈，以及怎样留下可追溯证据。

下面是解释职责的伪代码，不是Codex源码：

```harness
准备基础上下文：内置指令、AGENTS.md、技能目录、环境、工具定义
接收用户消息
while True:
    提交请求（初始上下文，或历史响应引用 + 新增内容）
    接收响应与流式事件
    保存响应ID与本地记录
    if 响应包含工具调用:
        按工具定义安排执行
        收集输出、退出码或错误
        使用call_id构造工具结果
        将工具结果加入上下文
    else:
        显示回答
        break
保留会话状态，等待下一条用户消息
```

本次没有展示显式审批、子智能体、重试、断线恢复或压缩流程；不要将其当成已掌握这些机制的证据。配置里列出这些能力也不代表实际执行过。

## 11. 实测计数与调用对照

下表来自response.usage，表示上游报告的token数，不是费用计算，也不能与JSON字节数混用。
